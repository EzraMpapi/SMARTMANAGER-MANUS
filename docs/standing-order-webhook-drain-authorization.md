# Production Dead-Letter Drain Authorization

**Status:** Design and migration contract. No production drain is enabled by this document.

## 1. Authorization objective

A production dead-letter drain can release provider callbacks toward financial settlement. It therefore requires two distinct human operators, two independent high-entropy secrets, explicit provider-account scope, bounded item and settlement caps, a short expiry, and a one-use final execution token. A service-role credential alone is not sufficient authorization.

The first operator is the **requester**. The requester creates a drain approval request for one provider, one non-secret merchant-account scope, one environment, one mode, and fixed caps. The second operator is the **approver**. The approver independently reviews the reason, queue evidence, provider status, financial preflight, and requested caps, then approves or rejects the request. The worker can open a production run only when the final approval is approved, unexpired, scope-matched, requester-bound, and backed by the final token hash.

## 2. Workflow

| Step | Actor | Required action | Durable state |
|---|---|---|---|
| 1. Detect | Monitoring/on-call | Identify quarantine flood or dead-letter condition; pause affected provider account if needed | No approval yet |
| 2. Prepare evidence | Requester | Produce bounded dry-run classification, oldest-item age, provider status, and accounting preflight | Evidence IDs and report reference |
| 3. Request | Requester | Generate a request token; submit only its SHA-256 hash with scope, caps, expiry, and reason | `REQUESTED` |
| 4. Review | Approver | Use a separate operator identity and separate approver token; verify provider/account, classification, conflicts, and financial risk | Pending approval |
| 5. Approve | Approver | Submit request-token hash, approver-token hash, final execution-token hash, approval reason, and approver identity | `APPROVED` |
| 6. Execute | Worker | Present final execution-token hash, requester identity, approval ID, exact scope, and caps | Approval becomes `CONSUMED`; drain run opens |
| 7. Drain | Worker | Lease bounded batches and process only allowlisted safe items | `OPEN`, then `COMPLETED`/`PAUSED`/`ABORTED` |
| 8. Close | Worker/operator | Verify no active leases, no duplicate accounting outcomes, and backlog disposition | Final audit record |

The request and approval must be separate actions. The requester must not approve their own request. A single operator, automation process, or shared credential must not satisfy both roles.

## 3. Token requirements

The three token roles are deliberately separate:

| Token | Generated by | Stored as | Purpose |
|---|---|---|---|
| Request token | Requester-side secret manager or secure CLI | SHA-256 lowercase hex in `request_token_hash` | Proves the approval request being reviewed is the one created by the requester |
| Approver token | Approver-side secret manager or secure CLI | SHA-256 lowercase hex in `approver_token_hash` | Proves a distinct approval action was performed |
| Final execution token | Approval service after both checks | SHA-256 lowercase hex in `approval_token_hash` | One-use bearer proof presented by the worker when opening the drain |

Each token must be generated from at least **32 cryptographically random bytes** using a CSPRNG, encoded with a transport-safe representation, and never derived from a username, timestamp, provider reference, approval ID, or other predictable value. The plaintext must be delivered only through an approved secret manager or process environment with restricted access. It must never be logged, stored in source control, placed in a URL, included in a webhook payload, or pasted into an incident channel.

The database stores only lowercase SHA-256 hex digests. The digest is computed over the exact UTF-8 token bytes. The final execution token must be different from both the request and approver tokens. The request-token hash, approver-token hash, and final-token hash must be pairwise distinct. Hash equality is rejected by the approval function.

The final execution token is single-use. The approval transitions from `APPROVED` to `CONSUMED` in the same transaction that opens the drain run. A second open attempt with the same approval ID or token must fail. The approval is also bound to `provider`, `provider_account_key`, `environment`, `mode`, `max_items`, `max_settlements`, and the requester identity. Increasing a cap, changing the provider account, switching environments, or changing the mode requires a new request and a new two-person approval.

## 4. Lifetime and revocation

Production approvals should expire no later than **15 minutes** after request creation. Staging approvals may use a longer but still bounded window, not exceeding **60 minutes**. The expiry is checked against database time, not worker wall-clock time. A request expires automatically when an approval attempt observes `expires_at <= now()`; it may also be explicitly rejected or revoked before expiry.

The final execution token may be used only once. If the worker crashes before opening the run, the approval remains `APPROVED` and an operator may retry within the expiry window. If the worker opens the run, the approval is `CONSUMED` even if the worker later aborts; recovery requires a new approval. This prevents an uncertain run from being replayed under the same human authorization.

Revoke the approval immediately when the provider account is suspected compromised, the provider status changes, the requested caps are no longer appropriate, the incident scope changes, or either token may have been exposed. Do not recover by changing the approval row directly; use a service-only revocation function that records the actor, reason, and execution ID.

## 5. Approval review checklist

The approver must independently verify the following before approving:

1. The affected provider and provider-account scope are exact and not a wildcard.
2. A dry-run report exists and its event IDs, classifications, oldest age, and conflict counts are bounded.
3. No `CONFLICT`, `FIELD_MISMATCH`, `SECRET_SUSPECTED`, or unknown provider state is included in the proposed settlement set.
4. Provider status, provider reference/UUID, client reference, amount, and currency match the trusted outbound transaction for every proposed safe item.
5. The accounting preflight shows no existing bank transaction or journal outcome for the proposed event.
6. The item and settlement caps are appropriate for the observed backlog and never exceed policy maximums.
7. The provider-account pause/kill switch is available and tested.
8. The requester and approver are different authorized operators.
9. The approval expiry is short enough for the incident and no longer than policy.
10. The approver records a human-readable reason without including secrets or raw provider payloads.

Approval is not permission to bypass provider signature verification, tenant correlation, identity comparison, or service-only settlement idempotency. It only authorizes a bounded drain after those controls pass.

## 6. SQL/API contract

The request bridge accepts `p_request_token_hash`, not plaintext. The approval bridge accepts the approval ID, request-token hash, approver-token hash, final-token hash, distinct approver identity, and approval reason. The worker’s open bridge accepts the approval ID, final-token hash, requester identity, exact scope, caps, and execution ID.

The database must reject:

- a requester approving their own request;
- an approver using the request-token hash as the approver token;
- a final token equal to either other token;
- an expired, rejected, revoked, or already consumed approval;
- a requester identity different from the original requester;
- a provider/account/environment/mode mismatch;
- worker caps above approved caps;
- production mutation without an approval ID and final-token hash;
- re-use of the approval ID or final token.

All three public bridges are service-role-only and must be `SECURITY INVOKER` with a pinned search path. Browser roles receive no execute privilege and no table write privilege. Approval records and drain runs must be audited with non-secret scope, actor IDs, timestamps, status, caps, and reason codes.

## 7. Incident and recovery rules

If any duplicate financial posting, amount/currency mismatch, provider-identity conflict, or unexpected provider status occurs during a drain, the worker must abort the run and leave the provider account paused. No operator may repair the ledger with direct SQL. Accounting reversal and reconciliation follow the institution’s approved financial-control process.

A new drain run requires a new approval, even when the previous run was aborted without financial impact. Resumption requires engineering and MFI/finance operations approval, a clean test-tenant rehearsal where applicable, no unresolved critical alert, and a documented incident record.
