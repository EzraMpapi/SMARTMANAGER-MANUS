# Transactional Email Configuration

## Active application delivery provider

Application-originated transactional messages use the existing **server-side Resend HTTP API**. The shared `server/transactionalEmail.ts` service handles provider requests, professional HTML and text content, recipient validation, error mapping, and provider-acceptance confirmation. It is used by manual workspace email, team invitations, and scheduled dashboard reports.

| Required server secret | Purpose | Where it belongs |
|---|---|---|
| `RESEND_API_KEY` | Authenticates server-to-Resend requests | Project deployment secret only |
| `RESEND_FROM_EMAIL` | Verified sender address | Project deployment secret only |

Neither value may be placed in browser code, a `VITE_` variable, local storage, a committed `.env` file, or an API response. The supplied unclassified credential is intentionally not used by this project because its provider and authentication scheme were not established.

## Supported application flows

| Flow | Delivery status behavior |
|---|---|
| Workspace manual email | The Email Center creates a Sent entry only after the server receives a Resend acceptance ID. |
| Team invitations | Invitation delivery is recorded as `pending` only after acceptance; provider rejection remains `delivery_failed`. |
| Scheduled reports | Report dispatch sends branded HTML/text and the CSV/PDF attachment through the same server delivery service. |
| Invoice reminders | The invoice action prepares the branded secure Email Center message instead of opening a `mailto:` link. |

## Supabase Auth messages

Supabase Auth still owns password signup confirmation, email verification, recovery, and OAuth lifecycle mail. To use a different mailbox provider for those emails later, configure the provider in **Supabase Dashboard → Authentication → Email → SMTP Settings**. The provider configuration must include the actual SMTP host, port, encryption mode, username, password/API key, and a verified sender address. This application does not replicate these messages or bypass email confirmation.

Use the production application URL `https://bserp-dashbo-xgm6fauw.manus.space/app` in Supabase Auth redirect configuration, together with the relevant `auth` query destinations already generated by the app. Confirm the verified sender domain in the email provider before enabling production delivery.

## Operational checks

When testing, send only to an authorised internal recipient. A successful server response means the provider accepted the message, not that a recipient has opened it. If a provider request fails, the UI shows a failure and does not create a sent entry. Server logs record only the HTTP status and message category, never secrets, recipient body content, or provider credentials.
